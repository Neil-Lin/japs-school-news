# 發布驗收流程

## 本機檢查與公開產物

```sh
python3 scripts/build_site.py
python3 scripts/check_project.py
python3 scripts/build_site.py --output dist
git diff --check
```

以 HTTP 提供 `dist/`，並同時測試根路徑與 GitHub Pages 的 `/japs-school-news/` 子路徑。不要將專案原始碼目錄直接當成正式發布產物。

- 根頁與五校頁面能載入，校名、官網、manifest、圖示及雜湊資產路徑正確。
- 首次進入時排除教育局消息；全選含教育局消息、全不選顯示引導、恢復預設回到第一頁。
- 搜尋與分類共同作用，空結果、清除搜尋、翻頁、重開分享網址及瀏覽器返回均正確。
- 用鍵盤操作：跳至內容後焦點位於主內容；Space 切換 checkbox；Enter 翻頁後焦點位於公告標題；清除搜尋後回到搜尋框。
- 五校在 320px／390px 無水平溢出；390×844 首屏可見第一筆公告標題。另以瀏覽器真正的 200% 縮放檢查搜尋、分類、公告、附件與分頁，完成後還原縮放。
- 至少以 Chromium 與 WebKit 核對主要流程；無障礙樹能辨識分類群組、勾選／半選狀態、頁碼與簡短結果通知。完整 VoiceOver 及行動裝置 PWA 安裝／更新仍須另行實測。
- 已連線閱讀學校後，停止伺服器並重新載入，可使用舊快照搜尋及切換已儲存學校；畫面顯示使用上次資料。恢復伺服器後可正常讀取。
- UI 資源變更會更新 CSS／JS 或 shell 版本；只有資料變更時不更新 shell。對比應涵蓋 placeholder 與各瀏覽器原生 checkbox 的勾號。

## PR 與 GitHub Actions

1. 發布前取得目前遠端 main，整合排程 bot 在本機工作期間產生的資料，重新驗證；不要覆寫較新的遠端資料或檢查時間。
2. 提交程式、模板、工作流程及需追蹤的產生檔；不提交忽略版控的 `static/`、`dist/`。由 PR 執行 **Project checks**，確認完整測試與公開產物打包通過。
3. 核對 Pages 建置來源為 **GitHub Actions**、部署環境允許 main、RSS bot 可以依分支規則提交資料。
4. 合併至 main 後確認 **Deploy Pages** 成功，且上傳來源為 `dist/`，程式碼部署不抓 RSS。
5. 在新版 main 手動執行 **Update RSS data**，確認資料更新／驗證／提交成功，再確認其成功完成事件接續 **Deploy Pages**。來源部分失敗應保留歷史並提示；全數失敗應使更新失敗而不改寫資料。
6. 正式站核對五校、預設分類、搜尋、分享網址、資料時間與新資產；確認既有 PWA 更新後仍能閱讀離線快照。保存實際 PR、commit、Actions run 與部署網址。

本機測試或遠端舊工作流程成功，都不能替代新版工作流程的實際執行紀錄。

## 午餐資料層驗收

- 本機執行 `python3 scripts/update_lunch.py --report /tmp/lunch-attempt.json`，確認五校學校代碼、餐日、供餐商、菜色及食材正確，再執行完整離線檢查與打包。午餐設定檔、更新器及診斷 report 不應出現在 `dist/`。
- 在新版 main 手動執行 **Update lunch data**，驗證 GitHub runner 能公開讀取官方介面、提交僅涉及 `data/lunch/` 與必要的公開檔案清單，並確認成功事件接續 **Deploy Pages**。目前尚未完成這項雲端驗收，不啟用排程。
- 部分失敗保留該校原快照與成功時間；全校皆失敗或不完整時不改寫任何公開檔案，工作流程失敗並留下 `lunch-attempt` artifact。同日菜單已存在時的空回應也不可清掉菜單。
- 午餐資料更新不得改動 RSS 檔案或 shell 版本。午餐視窗已完成本機驗收；正式版仍需核對快照雜湊、跨日舊資料提示、午餐失敗時公告可正常閱讀，以及 iPhone／iPad Safari 的關閉與返回操作。

## 發布失敗處理

- **PR 檢查失敗**：依輸出區分產生檔未更新、語法／測試或資料契約錯誤，修正後重跑。
- **RSS 更新失敗**：檢查來源狀態、資料驗證與 push 結果；遠端 main 前進時重新執行，不強制推送。
- **午餐更新失敗**：查看 `lunch-attempt` artifact 中的學校、供餐商及菜色錯誤；全數失敗保留原公開資料。若 main 已前進造成 push 失敗，重新執行，不覆蓋其他資料更新。
- **Pages 失敗**：先區分打包驗證與部署 job，核對 Pages 設定／環境／權限。流程內已有一次部署重試，失敗後檢查原因再重跑。
- **已發布版本有問題**：以 Git 的回復提交還原對應程式與產生檔，再由正常 main 部署流程發布；資料快照須保持契約一致，避免只回復部分 schema 檔案。
